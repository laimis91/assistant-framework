## Problem and intended outcome

`assistant-security` already requires reachable attack paths, redacted evidence, severity and authorization (`skills/assistant-security/SKILL.md:13`, `:26`, `:37`), but its four references are generic and web-oriented: endpoint greps for .NET/Node (`attack-surface.md:17-31`), OWASP web categories (`code-review.md:20-56`), CVE scanners (`dependency-audit.md:17-34`). Nothing covers this framework's actual risk surfaces: untrusted content steering agents and tools, delegated authority, approvals that must survive resume/retry, durable context, installer ownership of user files, and release provenance. The root rule "Separate demonstrated behavior from assumptions" (`SKILL.md:26`) has no defined state for a source-grounded hypothesis that needs runtime or deployment facts, and a full audit has no method for stating what it did not cover.

Separately, no skill covers maintainers triaging an incoming security advisory, where the characteristic failure is closing a report because `main` is fixed while a shipped release is still affected.

Intended result: Security analyses of agent, installer and release surfaces name a concrete crossed boundary and classify each item as confirmed or needs-validation; full audits state assessed versus blocked/excluded surfaces and do not over-claim coverage; and a new instruction-only `assistant-advisory-triage` skill produces a trust-model-first, shipped-release-proven verdict without taking any external action the user did not authorize.

## Requirements

### Part 1 — Security companions

- **R-S06-1. Selected companions.** `assistant-security` gains focused references for (a) agent/tool authority and durable context, (b) installer and filesystem ownership boundaries, and (c) dependency and release provenance. The root reference table (`SKILL.md:17-22`) lists each with its focus, and the root loads one only when the assessed target has that surface. An ordinary web or API security request loads none of them.
- **R-S06-2. Agent/tool authority and durable context.** The agent-authority companion directs the analyst to:
  - treat web pages, files, tool output, MCP metadata, retrieved or remembered content and delegated-agent returns as untrusted input;
  - report prompt injection only when a deterministic boundary fails: content reaches another principal's context, invokes authority the requester lacks, drives a sink the requester cannot reach, or causes an action the affected principal did not request or approve;
  - not count an instruction-only guardrail as an enforced boundary, and keep "instructed" distinct from "enforced" (for example, prompt guidance versus `codex-rules/workflow.rules` decisions and agent `tools:` lists);
  - check delegated authority: which identity and tools a subagent or role receives (for example `agents/claude/*.md` `tools:` lines) and whether its returns are treated as untrusted;
  - check action-approval binding: an approval binds the exact action, arguments and target, and a retry, resume or post-compaction continuation must not widen it or repeat a side effect;
  - trace each durable context store (memory notes, persisted task state, installer-managed instruction blocks) from every writer to every later reader that makes a privileged decision.
- **R-S06-3. Installer/filesystem ownership boundaries.** The installer companion directs the analyst to check, before any write, each class of ownership boundary: managed marker blocks (exact full-line, balanced, non-nested, non-duplicate markers), symbolic and hard links at the leaf and every parent, shared roots containing unrelated siblings, source/target path equality or ancestry overlap (including a configured home such as `CODEX_HOME`), and user-owned sentinels. A confirmed preservation failure is shown by changed or missing sentinel bytes or a mutation that happens before rejection; preservation is shown by byte-identical sentinels and rejection before the first write. It also directs comparison with the sibling implementation (Unix versus Windows installer) for the same boundary.
- **R-S06-4. Dependency and release provenance.** The provenance companion directs the analyst to: show who can influence dependency resolution and which build or release consumes it (a vulnerable or mutable dependency alone is not a finding); follow artifact identity across source, build, test, release and installed copy; treat a checksum fetched from the same location as its artifact as not independent; treat CI configuration as authorization code; and identify which shipped release or tag actually contains a given fix. `dependency-audit.md` remains the scanner-based CVE method.
- **R-S06-5. Confirmed versus needs-validation.** Every reported security item is one of two states. **Confirmed**: the source trace and observed or bounded local evidence establish the lower-trust actor, the input or action, the crossed boundary, the affected principal or resource and the result; only confirmed items receive severity. **Needs-validation**: a specific source-grounded boundary hypothesis is blocked on a named runtime, deployment, provider or host fact; it states that fact and a safe check an owner can run, and carries no severity. Generic advice with neither state is not reported as a finding. Output location: `assistant-security` has no `contracts/` directory and its output shape is root prose (`skills/assistant-security/SKILL.md:35`), so the root text names a fixed report heading, **Needs validation**, under which every needs-validation item is listed with its blocking fact and safe check; confirmed items stay under the findings. Evals assert that heading (R-S06-6, R-S06-9 for the Review mapping).
- **R-S06-6. Structured output compatibility.** When structured output is requested, confirmed items keep the existing `findings` fields (`SKILL.md:35`); needs-validation items are reported separately under a `needs_validation` list (each entry: hypothesis, blocking fact, safe check) and never placed in `findings` with a severity. In prose output they appear under the **Needs validation** heading (R-S06-5).
- **R-S06-7. Full-audit coverage.** For an explicit full or comprehensive audit, the report lists assessed surfaces, blocked surfaces with their blocker, and excluded or out-of-scope surfaces with the reason. A "complete" or "no findings" coverage claim is made only when no in-scope surface is blocked or unassessed; otherwise the report is labelled partial. This is prose in the report; no ledger file or validator is added.
- **R-S06-8. No sandbox promise.** Security instructions do not claim OS-level isolation the host cannot enforce. Executing target scripts or installers stays within existing authorization, and fixture execution follows Review's `script-execution.md` rules by reference. If isolation the check needs is unavailable, the item is reported as needs-validation with a safe validation plan.
- **R-S06-9. Security versus Review boundary.** Review owns findings in a delivered diff, including its user-owned file rewrite probe (`skills/assistant-review/references/review-checklists.md:69`) and the fixture-execution exception (`script-execution.md:8-31`). Security owns threat, trust-boundary and ownership analysis, the confirmed/needs-validation classification, and requested audits. Review's security-specialist pass keeps loading the `assistant-security` perspective (`agents/claude/code-reviewer.md:73`) and may load a companion when the diff touches its surface. That pass returns the canonical Reviewer schema (same line), whose `findings` carry severity, so needs-validation items map to the schema's existing optional `observations` list (`skills/assistant-review/contracts/handoffs.yaml:915-927`, in `orchestrator_to_reviewer.return_fields`, `:732`: `description`, required `evidence_gap`, optional `follow_up`), never to `findings`. The blocking runtime, deployment, provider or host fact goes in `evidence_gap` and the safe owner check in `follow_up`. This matches the reviewer rule that speculative or low-evidence concerns go in Observations and do not block completion (`agents/claude/code-reviewer.md:77`). No Reviewer schema field is added. The Security companions link to the Review probe and execution rules rather than restating them; neither skill duplicates the other's checklist text.
- **R-S06-10. Audit cases are examples only.** The installer companion may use audit F1, F2, F4 and F5 as worked examples, stating their current status on main. S06 does not change `install.sh`, `install.ps1` or any installer test to repair them.

### Part 2 — assistant-advisory-triage

- **R-S06-11. User job and activation.** A new skill `skills/assistant-advisory-triage/` serves maintainers deciding what to do with an incoming security advisory, advisory draft or vulnerability report (for example a GHSA or CVE report). Its description states what it does and when to use it, in third person, key use case first, following `docs/specs/skill-activation.md` R-DESC-1 and R-DESC-2, and carries no `effort` or `triggers` metadata. The description length limit is the existing repository constraint that R-DESC-1 refers to and `tools/skills/validate-skills.sh` already enforces (`tools/skills/lib/validate-frontmatter.sh:50`, `:506-507`); this slice adds no size budget of its own. It does not activate for threat modelling, code vulnerability audits, implementing a known fix or writing release notes.
- **R-S06-12. Trust model first.** The skill reads the project's published security policy or trust model before judging the report. If the project has none, it says so and treats any trust-model premise as an explicit assumption. Prerequisites already inside trusted host, same-user, operator or plugin state are out of scope unless the policy says otherwise.
- **R-S06-13. Shipped-release proof.** The skill establishes, with commands or artifacts it actually inspected: the latest shipped release identity on each channel the project publishes (tags, package registry versions), whether the vulnerable code is present in that release (for example by reading the file at the tag), and whether any shipped release contains the fix (for example tag containment of the fix commit). "Fixed on main" without a shipped release containing the fix is never by itself a reason to close.
- **R-S06-14. Exploit path.** The skill decides whether the report shows a real boundary bypass, as opposed to prompt injection alone, same-user local control, or helper-level semantics that differ from documented configuration. Where that needs fresh code analysis, it hands off to `assistant-security` (R-S06-19).
- **R-S06-15. Duplicate check.** The skill searches existing published advisories, fixed issues and related pull requests for the same root cause before deciding, and names the canonical duplicate when one exists, or states what was searched when none is found.
- **R-S06-16. Verdict and close bar.** The verdict is one of `close`, `keep open`, or `keep open but narrow`. `close` requires one of: duplicate of an existing advisory or fixed issue; invalid against shipped behaviour; out of scope under the project's security policy; or fixed before any affected release. A real bug with an overstated severity is `keep open but narrow`.
- **R-S06-17. Hardening separated.** Any hardening suggestion is reported separately from the verdict as not required for closure, and is offered only when it is concrete, low-risk and preserves intended user workflows. A hardening change that would require a product or security-model change is labelled as such.
- **R-S06-18. Authority for external actions.** Triage is read-only by default. Reading advisories through the user's available access is allowed when the user asked for triage. Posting comments, closing, publishing or editing an advisory, requesting a CVE, or contacting the reporter happens only when the user's task authorizes that specific action; otherwise the skill returns draft text. The skill contains no clipboard actions, named-maintainer pauses, project-specific (OpenClaw) policy, or model-routing instructions.
- **R-S06-19. Handoffs.** Triage hands off to `assistant-security` for new reachability or exploit-path analysis of the implicated code, and to `assistant-workflow` when the user authorizes a fix. `assistant-security` points to `assistant-advisory-triage` when the request is to decide the disposition of an incoming report rather than to analyze code. Handoffs are instruction text; no `requires` dependency is declared.
- **R-S06-20. Output.** For each advisory the answer leads with the identifier or link and the verdict, then the evidence that decides it: trust-model reference, implicated code references, shipped-release facts with how each was established, duplicate search result, then the separate hardening note, any draft maintainer text, and what remains unverified.
- **R-S06-21. Instruction-only.** The skill ships `SKILL.md` and `evals/cases.json` only. It has no `contracts/` directory, because no tool, agent or persisted state consumes its output shape (`docs/skill-contract-design-guide.md:24-33`).
- **R-S06-22. Eval fixture.** `skills/assistant-advisory-triage/evals/cases.json` uses schema `2.0` with `activation_cases` meeting the existing adequacy rule (at least three entries, at least two normalized-distinct positives and one normalized-disjoint nearby negative; `tests/p0-p4/skill-eval-contracts.sh:36-57`), plus behaviour cases for R-S06-13, R-S06-16, R-S06-17 and R-S06-18.
- **R-S06-23. Distribution.** The skill is bundled in the default install on every supported agent and is installable alone with `./install.sh --agent <agent> --skill assistant-advisory-triage` or `.\install.ps1 -Agent <agent> -Skill assistant-advisory-triage`. No installer or profile change is needed (see Affected owners for the verification).
- **R-S06-24. Inventory consumers.** The S06 branch is green on its own: the same change adds the README `### assistant-advisory-triage` section, updates the derived "N first-class" counts (README.md:3, :353, the literal count at :701) and `docs/evals/skill-fixtures.md:22` with its fixture list, and adds the routing row (spec table and `routing.json`) plus at least three held-out positive cases so `validate_all` passes (list under Affected owners). It does not refreeze the held-out hash; the integration step reconciles the final count across merged slices (S06, S08, S09, S10, S11) and does one held-out refreeze, which matters only for held-out trial runs (`tools/evals/skill-activation/run_trials.py:83-88`). The held-out case changes go through the user's R-EVAL-3 review; model runs need fresh authorization.
