# S02 — Conditional instruction loading and maintenance

Status: **Accepted by the user**, 2026-11-06 (drafted and revised the same day). Baseline: main d11756d. Implemented on branch `fvi/s02-conditional-loading` under D1(a), merged to main as 840e15a (#86). Measured with context report schema 3.0: the common guide is 54 words shorter (`common_operating_guidance`); the Review entry boundary is 90 words longer (`selected_skill_entry_boundary`); a standalone medium+ review no longer loads `score-tracking.md` (227 words, a file count outside the reporter's boundaries).
Source: report "Recommended direction" ("Remove from ordinary loading"), "Status against main", §3 (removal table, Onboard/Docs recipes, documentation drift), §4 orders 2 and 8, §5 (context tool), §6 rows 1 and 27; slice map row S02; index "Report items not yet owned by a slice".

## Problem and intended outcome

Part of this slice has already landed. #76 moved the progress wire rules out of ordinary loading, and legacy Workflow compatibility was already conditional. Three problems remain. Review loads score-progression bookkeeping for every medium+ review, although scores are diagnostic only and cannot drive continuation or completion. README and several skills restate protocol rules that have a canonical owner, and README now contradicts current Research and Review roots. Docs and Onboard lack two small practical recipes the report recommends. The intended result: ordinary work loads only guidance relevant to it; persisted and delegated consumers keep their exact obligations; each protocol rule has one canonical owner that others link to; README matches current roots; and any claimed reduction in instruction load is measured over the boundary it claims.

## Requirements

- **R-S02-1 Record the landed split as existing behaviour.** The specification records that ordinary activities load `tools/progress/operating-guidance.md` and that only persisted/executable progress consumers load `tools/progress/wire-boundary.md`. No further split of the common guide is required by S02.
- **R-S02-2 Ordinary review does not load score bookkeeping.** The discriminator is whether Review's contracts are loaded, not who reads the result. Review loads `contracts/index.yaml` only "at structured boundaries" (`skills/assistant-review/SKILL.md:34`), and gate X3 (`contracts/phase-gates.yaml:360-363`) is part of those contracts, so X3 binds only when contracts are loaded at a structured boundary. A review with no structured boundary (no contract load, task journal or QA consumer) does not load `score-tracking.md` or compute score-progression or drift labels. Where contracts are loaded, X3's condition `scope_size in [medium, large]` still applies unchanged, and `rubric_summary` (with score progression), `rubric_scores` and journal score lines are produced exactly as today until D1 changes them. Source does not state whether a standalone medium review returned to the user is a structured boundary; the plan must state that it is not (D1(a)) and update the eval case `medium-review-requires-rubric` (`skills/assistant-review/evals/cases.json:693-744`), whose expected behaviour "Includes score progression when multiple rounds occur" (`:709`) assumes score bookkeeping on a standalone medium review. Rubric dimension scores in that case (`:705`, `:713`) come from `review-rubric.md`, not `score-tracking.md`, and are outside R-S02-2.
- **R-S02-3 Score-tracking content that is not bookkeeping keeps an owner.** Rules now hosted in `score-tracking.md` that are not score arithmetic keep a canonical owner before the file is narrowed or removed: the pivot/restart routing (`pivot_restart_signal`, Pivot/Restart Decision Packet) and "score diagnostics alone do not" trigger a decision. The shared-guard restatement is replaced by a link to the common guide.
- **R-S02-4 Removed or weakened score fields follow the contract guide.** Removing or weakening any required score field (`rubric_summary.score_progression`, `rubric_scores`, the X3 gate, Workflow R6) requires a major `schema_version` bump, a migration note in `SKILL.md`, and updated consumers, evals and mirrors (`docs/skill-contract-design-guide.md:120-124`). Historical records keep their labels and stay readable.
- **R-S02-5 One canonical owner per protocol rule.** Where README or a skill restates a rule that has a canonical owner (the shared stagnation guard, review round rules, workflow plan modes, version labels), the restatement is replaced by a link plus at most the task-relevant explanation the reader needs at that point. Agent definitions and other delegated consumers that do not load the canonical file keep their self-contained obligations.
- **R-S02-6 README matches current roots.** README describes Research and Review as their current roots do (no "tiered information gathering with confidence scoring", no "calibrated scores and finite rounds", no tier list for `research.md`, no "standard-tier research" example). Other README statements found to contradict current roots during the change are corrected or listed.
- **R-S02-7 Drift regression check.** The existing README stale-wording check is extended to reject the corrected phrases, so the drift cannot silently return.
- **R-S02-8 Optional Onboard inventory recipe.** Onboard offers an optional recipe for a language/size inventory when the user asks for one or the repository is unfamiliar and large. It respects Git ignores, excludes dependency, build, vendored and generated directories explicitly, prefers tools already available, and reports instruction/Markdown files separately from code. Counts are orientation facts, never quality scores. It installs nothing without authorization.
- **R-S02-9 Concise Docs editing checklist.** Docs offers a short editing checklist for revising prose. It preserves meaning and accurate technical terms; matches the target document's existing voice, or a user-supplied sample; removes unsupported significance claims, vague attributions, promotional language, filler and generic conclusions; and shows the change as a diff or changed section. Coverage and relevance remain owned by S01. The checklist contains no word blacklist used as a pass/fail gate, no forced personal voice and no mandatory second critique pass.
- **R-S02-10 Honest instruction-load measurement.** Any S02 claim of reduced instruction loading names the measured boundary and states which loaded components it excludes. A total that excludes the common guide's body is not presented as the full per-activity load.

## Unresolved decisions

- **D1 How far to retire review score bookkeeping (product_question).** Options:
  - (a) Conditional loading only. `score-tracking.md` loads when Review contracts are loaded at a structured boundary (`assistant-review/SKILL.md:34`), where X3 or a journal requires `rubric_summary` or score lines. Contract text, including X3's condition, is unchanged and there is no schema bump. Cost: the standalone-review eval case `medium-review-requires-rubric` (`assistant-review/evals/cases.json:693-744`, score-progression expectation at `:709`) must be updated to drop score progression for a standalone review returned only to the user, and the plan must state explicitly that such a review is not a structured boundary. If the plan finds that standalone medium reviews do load contracts, (a) cannot remove score progression from them without changing X3, and that change belongs under (b).
  - (b) (a) plus making `rubric_summary.score_progression` and gate X3 optional (or narrowing X3's `scope_size in [medium, large]` condition), and Workflow R6 advisory. This weakens required fields, so Review moves to schema v11 with a migration note, consumers, evals and mirrors updated, and historical v10 records readable.
  - (c) Retire review rubric scoring entirely (`rubric_scores`, `rubric_summary`, `review-rubric.md` thresholds), keeping concrete findings, coverage and acceptance as completion controls.

  Recommended: (a) now. It removes ordinary loading without a contract or schema change; its compatibility cost is the one eval-case update above plus the explicit structured-boundary statement. Decide (b) or (c) after the plan inventories real readers of `rubric_summary` beyond tests: none outside Review contracts, agents, Workflow R6, journal templates and the harness guide were found. **Decided by user 2026-11-06:** option (a), load score bookkeeping conditionally (the recommended default).
