## Problem and intended outcome

assistant-debugging requires the smallest safe reproduction and a symptom match, but gives no method for building one when no ready test exists, and no way to inspect runtime state when logs cannot settle a question. Agents therefore fall back on speculative edits or repeated logging. The change adds a reproduction (feedback-loop) reference and short Python, Node and .NET state-inspection recipes, loaded only when needed. The .NET recipes were added by the user's decision of 2026-11-06 (Unresolved decision 3); shell-script recipes remain a later proposal. Observable result: a representative failure becomes reproducible for the right reason, and a nearby unrelated failure does not satisfy the same reproduction check.

## Requirements

- **R-S03-1** Debugging gains a reproduction reference that helps choose a feedback loop among: an existing failing test, a CLI or HTTP probe, replay of a captured trace or payload, a small harness around the failing path, a controlled reproduction of a flaky failure, bisection between a known-good and known-bad state, and differential comparison of two versions, configurations or inputs. Selection is by fit to the symptom and cost; the list is not an order to work through.
- **R-S03-2** The reference requires the reproduction check to assert the exact reported symptom (the specific wrong value, error identity, message or state) rather than a generic signal such as "non-zero exit", "test failed" or "exception raised".
- **R-S03-3** The reference explains how to confirm the check is specific: identify a nearby unrelated failure (for example a setup, import, fixture or different-assertion failure on the same path) and confirm it would not satisfy the check. Where the check cannot distinguish them, the reproduction is recorded as `partial`, not `yes`. This uses the existing enum value (`contracts/output.yaml:75-79`) but gives it new semantics: today the field is described only as "Whether the reported symptom was reproduced" (`:79`), with no rule that a non-discriminating check is `partial`. It is therefore an explicit change to the meaning of `yes` and `partial`, handled under Unresolved decision 5.
- **R-S03-4** The reference covers reducing setup cost (narrow scope, skip unrelated initialisation, reuse fixtures) and controlling timing and randomness (pinned clock, fixed seed, isolated filesystem/network, markers or barriers for interleaving), and records observed repetition counts for flaky reproductions instead of a target rate.
- **R-S03-5** The reference covers minimising the reproduction: remove inputs, steps, configuration or data one change at a time and re-run the check after each cut; a cut that removes or changes the exact symptom is restored. A minimised reproduction may become the regression oracle handed to Verification/TDD.
- **R-S03-6** Debugging gains short state-inspection recipes, used only when a specific state question remains that the reproduction, traceback or logs cannot answer:
  - Python: full traceback and locals in failure output, post-mortem inspection, `pdb`/`breakpoint()`, and `debugpy` attach when a long-lived or remote process must be inspected.
  - Node: inspector launch/attach, breakpoints, child-process inspection, and source maps for transpiled code.
  - .NET (added by user decision 2026-11-06, see R-S03-13): reading the full exception chain and stack trace from test output, re-running one test with `dotnet test` and a test filter at a verbosity that prints the full failure, and, only for a question those cannot answer, a process dump or trace with `dotnet-dump`/`dotnet-trace` when already installed, or a debugger attached by the user through their IDE.
- **R-S03-7** The recipes prefer non-interactive or scripted inspection where the agent's shell cannot drive an interactive prompt, and state that an interactive pause under an output-capturing runner or non-TTY shell can hang the process.
- **R-S03-8** Inspection ports bind to loopback only. The recipes read the actual debugger endpoint from the target process's output instead of assuming a default port or the presence of a helper package; any helper (for example `debugpy`, a CDP client, `dotnet-dump` or `dotnet-trace`) is used only after confirming it is available, and none becomes a mandatory dependency.
- **R-S03-9** Before handoff, every debugger session started for diagnosis is resumed or terminated, and temporary breakpoints, `breakpoint()`/`set_trace()` calls and inspector flags added to source or configuration are removed; the result reports any that could not be cleaned up.
- **R-S03-10** Bisection and other history-moving techniques run without resetting, stashing or overwriting the user's uncommitted work (for example in an isolated worktree), and destructive, production-affecting, network or sensitive diagnostics keep their existing authorisation requirement.
- **R-S03-11** The SKILL.md entrypoint links each new reference with its load condition (reproduction reference: no adequate exact-symptom reproduction exists yet; inspection recipes: an unresolved runtime-state question in Python, Node or .NET). Work that already has an exact-symptom reproduction loads neither.
- **R-S03-12** Repeated reproduction or inspection attempts are governed only by the shared stagnation guard; the references add no attempt count, hypothesis quota or escalation threshold.
- **R-S03-13** (.NET recipes; user decision 2026-11-06.) The .NET section is short and follows the same safety rules as Python and Node (R-S03-7 to R-S03-10), with these .NET specifics:
  - **Exception and stack first.** Start from the exception type, message, inner exceptions and stack trace already printed by the failing test or process (the full `Exception.ToString()` form). Re-run only the failing test with `dotnet test` and a `--filter` on its fully qualified name, at a console verbosity that prints the full failure, before reaching for any other tool. `dotnet test` is already an allowed command (`skills/assistant-workflow/references/ai-usage-policy.md:84`). Exact flag spellings (`--filter` expressions, the console logger verbosity form, `--diag`) are checked against current Microsoft documentation during implementation (Evidence classification). Runner diagnostic logs (`--diag`) are used only when the test runner itself misbehaves, are written outside the repository, and are deleted or reported under R-S03-9.
  - **Tools only when already installed.** `dotnet-dump` (dump capture and analysis, for example managed stacks of all threads for a hang) and `dotnet-trace` (event traces) are used only after confirming they are already on the machine (for example `dotnet tool list -g` or a `command -v` check). Nothing in the repository installs or assumes them (grep for `dotnet-dump`, `dotnet-trace`, `dotnet-counters`, `vsdbg` and `netcoredbg` over the tree at d11756d finds none outside this specification set). The recipe states its own rule rather than relying on Workflow being loaded: if a needed tool is missing, the agent asks the user before installing it, waits for an explicit yes, and never installs it on its own; without that answer it uses the exception-and-stack route or reports the blocker. This matches Workflow's policy, which lists "Installing packages or dependencies" as requiring user confirmation (`skills/assistant-workflow/references/ai-usage-policy.md:90`), kept here as evidence; Debugging does not depend on that file being loaded.
  - **Dumps and traces are sensitive diagnostics.** A process dump holds process memory, and a `dotnet-trace` event trace can record arguments, paths, environment-derived values and other runtime data; either may contain secrets or private data. Capturing one keeps the existing authorisation requirement for sensitive diagnostics (`skills/assistant-debugging/SKILL.md:41-43`). Dump and trace output is written outside the repository, never committed, never quoted beyond the stack, events or values needed, and deleted at handoff or reported under R-S03-9.
  - **Local only.** Dump and trace tools attach through the runtime's local diagnostics channel to a process the same user owns. The recipes configure no TCP diagnostic port and no remote debugger (for example remote `vsdbg` over SSH); a remote target is a network diagnostic needing authorisation under R-S03-10. Attach never needs root, `sudo` or a ptrace setting change; if attach is refused, the recipe reports the blocker instead of weakening `ptrace_scope` or elevating.
  - **Interactive debugging is the user's.** The agent cannot drive an IDE debugger. When stepping through code is the only way to answer the state question, the recipe gives the user exact attach steps for their IDE (process, breakpoint location, what to read) and waits for the observed value. Inserted `Debugger.Launch()`/`Debugger.Break()` calls are temporary source changes covered by R-S03-9 and are avoided under a non-interactive runner (R-S03-7).

## Unresolved decisions

1. **One file or two?** (technical default) Options: (a) `references/reproduction.md` plus `references/state-inspection.md`; (b) one file with two sections. Recommend (a): the load conditions differ (R-S03-11), and inspection recipes are runtime-specific.
2. **Index load set?** (technical default) Options: link from SKILL.md only; or also add `reproduction`/`state_inspection` load sets to `contracts/index.yaml`. Recommend SKILL.md links only, since no structured consumer selects these files; add a load set later only if a persisted/delegated consumer needs it.
3. **Other runtimes** (product_question) Should recipes cover .NET (the repo's C# tooling) or shell scripts? The accepted scope named Python and Node only; the draft recommended Python and Node only. **Decided by user 2026-11-06: Python, Node and .NET; shell later.** The .NET recipes are R-S03-6 and R-S03-13; shell-script recipes are recorded under Scope and non-goals as a later proposal.
4. **Minimisation stop rule** (technical default) Recommend "reduce while the exact symptom persists and each cut still materially shrinks the loop" over strict one-minimality, to avoid an open-ended cost; no numeric bound.
5. **Compatibility handling for the new `partial` meaning** (technical default) R-S03-3 narrows `yes` (now requires a discriminating check) and widens `partial`. No value is removed and no field is weakened, so the contract guide's major-bump rule for removing or weakening required fields (`docs/skill-contract-design-guide.md:120-124`) does not strictly apply, but the change is to a serialized contract and needs a recorded compatibility decision. Options: (a) update the `reproduced` description in `contracts/output.yaml:79` to define `partial` as "symptom observed, but the check does not distinguish it from a nearby unrelated failure, or only part of the symptom was observed", state in that same description that historical `yes` records may predate the discrimination rule, keep `schema_version` "3.0", and optionally add a one-line pointer in `SKILL.md` to that contract description (the description, not SKILL.md, holds the definition and the historical-`yes` note); (b) as (a) but bump all Debugging contracts to "3.1" with the same note; (c) add a separate optional field (for example `discriminating_check`) and leave `partial` unchanged. Recommend (a): the enum is unchanged, all listed consumers keep validating, and historical records stay readable with the note.
   **Carried copies.** Workflow `debugging_result.reproduction_status` (`skills/assistant-workflow/contracts/output.yaml:340-343`) and TDD `debugging_evidence.reproduction_status` (`skills/assistant-tdd/contracts/input.yaml:70-73`) carry the same value. Options: (i) copy the Debugging `reproduced` description's `partial` definition and historical-`yes` note, word for word, into each field's description, keeping Workflow output "16.0" and TDD input "3.0"; (ii) leave them undescribed and rely on the Debugging definition; (iii) bump their schema versions as well. Recommend (i): the three fields then mean the same thing, and no version bump is needed because no enum value, requiredness or gate behaviour changes. A bump is needed only if implementation changes what a gate accepts. TDD's RED precondition (`skills/assistant-tdd/contracts/input.yaml:67`) must keep requiring the evidence or a documented blocker and must not be reworded so that `partial` alone becomes sufficient evidence of the reported symptom for RED; Workflow build-worker routing (`skills/assistant-workflow/references/build-worker-protocol.md:301`) keeps tracing RED to the original reproduction evidence.
   **Compatibility record.** The change records: affected fields `reproduction.reproduced` (Debugging output "3.0"), `debugging_result.reproduction_status` (Workflow output "16.0"), `debugging_evidence.reproduction_status` (TDD input "3.0"); change type: description-only meaning change of `yes`/`partial`; enum, requiredness and gates unchanged; no version bump; historical `yes` records stay readable with the note; fixtures checked as above.

## Acceptance examples

- **R-S03-1/2 positive:** User reports "checkout total is 800 instead of 900 after a 100-cent promotion". The agent writes a test or CLI probe asserting `total == 900` against a replay of the order and observes `800`. Passes.
  **Negative:** The agent's check is "run the checkout suite; it exits non-zero". Fails R-S03-2.
- **R-S03-3 positive:** The same probe is run with a deliberately broken fixture path; it errors with a fixture error, which the agent confirms does not match the exact-symptom assertion. Recorded `reproduced: yes`.
  **Negative:** A tax-rounding failure producing `899` would also make the check fail because it only asserts `total != expected-from-old-run`; the agent nonetheless records `reproduced: yes`. Fails.
- **R-S03-4 positive:** A flaky ordering failure is reproduced with a fixed seed and a barrier; result recorded as "failed 7 of 40 runs with seed 1234". Passes.
  **Negative:** "Added `sleep(2)` and it failed once, so the race is confirmed." Fails (sleep used as proof; no counts).
- **R-S03-5 positive:** Removing the coupon list leaves `800`; removing the promotion makes the total correct, so the promotion is restored and kept. Passes.
  **Negative:** A cut changes the failure to a `KeyError`, and the agent keeps the cut and continues. Fails.
- **R-S03-6/7 positive:** For a Python `KeyError` deep in a call chain, the agent re-runs the single test with full traceback and locals, then uses a scripted post-mortem to print the dict keys. Passes.
  **Negative:** The agent inserts `breakpoint()` and runs the test under a capturing parallel runner in a non-interactive shell, which hangs. Fails.
- **R-S03-8 positive:** Node is started with an inspector bound to `127.0.0.1` on an automatic port; the agent reads the `ws://` URL from the process output. Passes.
  **Negative:** The agent binds `0.0.0.0`, or assumes port 9229 after requesting a random port, or installs a global CDP package without asking. Fails.
- **R-S03-9 positive:** Result states "inspector target terminated; temporary `breakpoint()` removed from `cart.py` (git diff clean for that file)". Passes.
  **Negative:** Handoff leaves a paused child process or a committed `set_trace()`. Fails.
- **R-S03-10 positive:** Bisection runs in a separate worktree; the user's dirty checkout is unchanged. **Negative:** The agent stashes the user's changes to run `git bisect`. Fails.
- **R-S03-11 negative:** The user supplied a failing test that already asserts the exact symptom; the agent loads the reproduction reference anyway and rebuilds a harness. Fails the load condition.
- **R-S03-12 negative:** The reference says "after three failed reproductions, escalate". Fails.
- **R-S03-13 positive (exception first):** An xUnit test fails with `InvalidOperationException` from a nested call. The agent re-runs only that test with `dotnet test --filter "FullyQualifiedName~OrderTests.Applies_promotion"` at a verbosity that prints the full failure, reads the inner exception and the stack frame in `PromotionService.Apply`, and answers the state question without another tool. Passes.
  **Negative:** The agent reruns the whole solution repeatedly with `-v diag` and leaves `--diag` logs inside the repository. Fails.
- **R-S03-13 positive (hang, tool present):** A test host hangs. `dotnet tool list -g` shows `dotnet-dump` installed; with authorisation for a sensitive diagnostic, the agent captures a dump of the test host outside the repository, reads the managed stacks of all threads, finds a `.Result` blocking on a continuation, deletes the dump and reports the deletion.
