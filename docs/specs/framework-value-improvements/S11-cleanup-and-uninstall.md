# S11 — Legacy cleanup and uninstall

Status: **Accepted by the user**, 2026-11-06 (drafted and revised the same day). Baseline: main d11756d. Not implemented. Revised 2026-11-06 for the user's decision D-S11-8 ((b): installers auto-remove proven-owned retired skills and agents) and for S10's added `assistant-ideate` retirement.
Source: user decision of 2026-11-06 recorded in the slice map ("a separate cleanup skill that can be executed after installation and removes hooks, agents, skills etc. that are legacy; complete removal is an uninstall script"); slice map row S11 and its "Retirement facts" paragraph; report §3 Telos/Diagrams rows, §4 order 7, and the "Audit-backed examples" paragraph in report §E "Security" (F1/F2/F4/F5); audit /Users/laimis/Downloads/assistant-v1-project-audit.md F2, F4, F5.

## Problem and intended outcome

The installers copy framework skills, tools, eval docs, agents, Codex rules and a managed instruction block into agent homes. Neither installer can remove a retired skill or agent. Reinstalling leaves retired skill directories in place: on this machine at 2026-11-06, `~/.claude/skills/assistant-telos` and `~/.codex/skills/assistant-telos` still exist. Retirement today is a set of hard-coded per-installer lists covering hooks and a few tools, and the two installers' lists already differ. Ownership is decided by name alone. That is demonstrably unsafe: `assistant-memory` is a retired framework skill name (7e2fedd), and `~/.claude/skills/assistant-memory` and `~/.codex/skills/assistant-memory` now hold a *different* product's skill.

The intended outcome has three parts. First, a cleanup skill, run after installing a new version, reports the framework-owned legacy items in an agent home, then removes only those the user confirms that are proven framework-owned. Second, uninstall scripts remove every framework-owned item for a chosen agent on Unix and Windows. Third, both use one retired-item inventory that the installers also read. By the user's decision of 2026-11-06 (D-S11-8 (b)), the installers also remove proven-owned retired skills and agents automatically on every install, using the same ownership proof as the cleanup helper, and keep and report anything ambiguous for the cleanup skill (R-S11-25 to R-S11-27). User-authored and unrelated content stays byte-identical. Verification uses disposable homes with sentinels.

## Requirements

### Cleanup skill

- **R-S11-1. User job and activation.** A new first-class skill (working name `assistant-cleanup`; final name D-S11-1) removes legacy Assistant Framework items from an installed agent home after the user installs or updates the framework. Its description and activation cases follow docs/specs/skill-activation.md. Positive triggers: removing retired or legacy framework skills, agents, hooks or tools, or cleaning a framework installation after an update. Near-miss negatives that must not activate it: code cleanup, dead-code removal, refactoring, deleting project files, and uninstalling or removing software that is not the Assistant Framework. A request to uninstall the framework itself activates the skill, which then only gives the exact uninstall command for the user's platform and agent, to be run from the user's framework checkout (D-S11-6), and runs nothing (D-S11-4 (a), decided by user 2026-11-06). The installed skill cannot know where that checkout is: neither installer records its source path in the agent home (install.sh:795 and install.ps1:2671 resolve it only for the run, and install.sh:847 and install.ps1:2543 only print it). The command therefore uses a placeholder such as `<path-to-your-framework-checkout>/uninstall.sh --agent codex`, and the skill tells the user to replace it. That request is a positive activation case, not a negative one. It is bundled in the default install and installable alone with `--skill` (index "Distribution").
- **R-S11-2. What it detects.** For the selected agent (`claude`, `codex`, `gemini`) and the platform layout, cleanup looks only for items listed in the retired-item inventory (R-S11-16). The categories are:
  - retired skill directories (at minimum the earlier `assistant-memory` and `assistant-reflexion`, plus `assistant-telos`, `assistant-diagrams` and `assistant-ideate` from the S10 change that deletes their sources (S10 R-S10-18 adds Ideate); their entries land in that same change, never before, so a skill still in source is never an inventory entry; `assistant-memory` and `assistant-reflexion` were removed in 7e2fedd, before the inventory exists, so their entries are seeded with that historical revision under R-S11-19 rather than the same-change rule);
  - retired agent files, Claude `*.md` and Codex `*.toml` (none are retired at d11756d; the category exists so future retirements need no new mechanism);
  - retired hook entrypoints, helpers, modules and inert shims under `hooks/assistant`, and exact retired hook registrations in `settings.json` (Claude, Gemini) or `hooks.json` (Codex);
  - retired managed tools and source-only tools;
  - retired managed instruction blocks (`ASSISTANT_FRAMEWORK_MEMORY_PROTOCOL_START/END`).

  It never treats an item as legacy just because it is absent from the current source.
- **R-S11-3. Ownership proof before removal.** An item is removable only when all of these hold:
  - (a) its path is an inventory entry for this agent and layout;
  - (b) every file in it matches framework content (D-S11-2 settles the content proof: a released-content fingerprint, an installer receipt, or both);
  - (c) a directory item holds no file that fails (b);
  - (d) the item, and every ancestor up to the agent home, is a real file or directory, not a symlink, junction or other reparse point;
  - (e) for a registration or instruction block, the exact match rules already used by the installers apply: the first command token equals a known retired entrypoint path (install.sh:496-511 and 588-601, install.ps1:2016-2033), and the marker state is exactly one balanced block (install.sh:1141-1150, install.ps1:2199-2234). Of the installers' three first-token forms (R-S11-22 `items[].id`), the checkout form `<checkout>/hooks/scripts/<name>` (install.sh:472, 515; install.ps1:2020-2024) is matched only by the uninstall scripts, and only with `<checkout>` equal to the path of the framework checkout that uninstall is running from. The cleanup helper runs from installed tools and knows no checkout path (R-S11-1, D-S11-6), so it never matches that form: a registration whose first token ends in `/hooks/scripts/<retired name>` is reported as kept ambiguous, with the reason "possible framework checkout path; run uninstall from that checkout or remove it by hand". Uninstall reports the same way a checkout-form token naming a different checkout;
  - (f) for an inventory entry marked `installer_generated` (R-S11-19), (b) and (c) are replaced by an exact-location rule: the item is at exactly the entry's `root` and `path` and has the entry's `node_type`. Its contents are not compared, because the artefact was never tracked in source and has no content to fingerprint. This preserves the installers' current exact-path removal of `tools/evals/node_modules` regardless of contents (install.sh:726-727; install.ps1:2560, 2607). (a) and (d) still apply, and the deletion never follows a link inside the item. `tools/evals/node_modules` is the only item that the cleanup helper and the uninstall scripts remove without a content proof;
  - (g) **installers only.** For an inventory entry whose `installer_exact_removal` (R-S11-19) contains the current layout, `install.sh` and `install.ps1` keep their current exact-path removal without content proof: (b) and (c) are replaced, for the installers alone, by the exact-location rule of (f). This preserves what the installers do at d11756d, where they remove these retired tool paths whatever their bytes (install.sh:720-741, 726-729 and 743-776; install.ps1:2551-2566, 2604-2610), together with the per-path type and link guards they already apply (install.sh:743-760; install.ps1:1462-1604), neither strengthened nor weakened. The cleanup helper and the uninstall scripts never apply (g). For them such an entry still needs (b) and (c), or (f) when it is `installer_generated`, and an item whose content does not match is kept as ambiguous. (g) stays limited to the existing tool entries named in R-S11-19 `installer_exact_removal`. It never applies to a `skill_directory` or `agent_file` entry, which may not carry `installer_exact_removal`. Installers remove those only under R-S11-25, with the full content proof of (a)-(e).

  Any other state is **ambiguous**. The item is kept and reported with its reason. A name match alone never establishes ownership.
- **R-S11-4. Never removes.** Cleanup never removes or edits:
  - user-authored or unrelated items, including same-named items from other products;
  - a shared or container root (`skills/`, `tools/`, `docs/evals/`, `agents/`, `rules/`, `hooks/`, `~/.agents`, `~/.agents/skills`, `~/.agents/tools`);
  - current, non-retired framework items;
  - `config.toml`, `~/.claude.json`, credentials, session or history data;
  - any file outside the resolved agent home and, for Codex on Windows, the `~/.agents` roots;
  - Telos purpose files anywhere.

  It may delete a retired directory that becomes empty only when that directory is itself an inventory entry (precedent: install.ps1:1551-1604, install.sh:778-787).
- **R-S11-5. Report first.** Every run starts with a non-mutating report: what would be removed, what is kept as ambiguous (with reason), and what is kept as user or unrelated content found at an inventory path. The dry run also emits the removal manifest (R-S11-22): every item reported as removable, each with its path and a content digest, plus the manifest's own digest. The report shows the manifest digest beside the removable list. The dry run creates no files or directories inside the agent home or any inventory root, and changes no content, mode, ownership or modification time of any existing item; access times are excluded, because hashing reads files. The manifest goes to standard output, or to a caller-supplied path that resolves outside the agent home and every inventory root.
- **R-S11-6. Explicit confirmation for destructive removal, bound to the reported set.** Removal happens only after the user explicitly confirms the exact reported set in chat. This follows the installed guidance to stop for approval of "a destructive, external, or hard-to-reverse action" (install.sh:1112-1117). Chat confirmation is necessary but not sufficient:
  - Apply always takes the dry-run manifest and its digest as required input (`--manifest <file> --manifest-digest <digest>`, R-S11-22), whether or not it runs interactively. Apply without a manifest, or with a manifest whose recomputed digest differs from the confirmed digest, refuses and changes nothing.
  - Apply removes only items listed in that manifest. It never scans for further candidates to remove. An item that appears, or newly passes ownership proof, after the report is not removed, even if it is an inventory entry; at most it is reported as "not in the confirmed manifest".
  - Immediately before deleting each listed item, the helper re-proves ownership (R-S11-3) and recomputes the item's content digest. It skips, with a report line, any item whose type, link status, content or digest differs from the manifest.
  - **Registrations are re-proven and removed per settings file.** Removing one registration shifts the index of every later command in that event, and the installers' rewrite also drops groups and events left empty (install.sh:558, 561; install.ps1:2083-2097). So a `hook_registration` item's index and digest (R-S11-22) are always evaluated against one snapshot of its settings file, read once at the start of apply, before any change; they are never recomputed against a file from which an earlier item has been removed. All listed registration items in one settings file are re-proven together against that snapshot before any change to it. Only if every one of them passes are they removed together in one atomic rewrite of that file (temporary file beside it, then replace, preserving mode, as install.sh:520-568 and install.ps1:2106 with `Save-JsonObject` at 1847-1850 and `Write-AtomicText` at 887+ do), and only if the file's bytes still equal the snapshot at that moment. If any re-proof fails, or the file changed, that settings file is left byte-identical and each of its listed items is reported as skipped with its reason. Other settings files and other items are handled independently.
  - The helper's own confirmation rule (R-S11-23) and the Codex `prompt` rules (R-S11-24) apply in addition.

  Host permission prompts stay in force, and the skill does not bypass them. The Codex `rm -rf` prompt rule (codex-rules/workflow.rules:57-60) is not weakened or allow-listed. That rule matches only the `rm -rf` argv prefix, and a helper deletes through language APIs that the prefix rule never sees, so the chat confirmation is never the only safeguard. The deterministic safeguards are the helper's manifest and digest binding and its confirmation rule, which hold on every agent, plus the Codex prompt rules of R-S11-24 where Codex enforces them.
- **R-S11-7. Coverage.**
  - **Claude:** `~/.claude`.
  - **Gemini:** `~/.gemini`.
  - **Codex:** the configured `CODEX_HOME`, else `~/.codex` (install.sh:810-817; install.ps1:2485-2491). On Unix this includes the `~/.agents` → agent-home symlink (install.sh:902-919). On Windows it includes the separate real `~/.agents/skills` and `~/.agents/tools/{change-impact,progress}` roots (install.ps1:2508-2513, 2619-2623).
  - **Unix and native Windows:** the Windows path refuses Codex work while Codex is running (install.ps1:152-161), as the installer does.
  - The skill resolves the configured home. It never hard-codes `~/.codex` (audit F7 lesson).
- **R-S11-8. Deterministic helper.** Ownership checks, report generation and removal run in a deterministic helper per platform, which the skill calls with dry-run and then apply arguments. Apply always requires the dry-run manifest and its digest (`--manifest` and `--manifest-digest`, R-S11-22), and additionally the confirmation of R-S11-23; an interactive prompt is an extra check on top of that binding, never a substitute for it. The skill does not compose ad hoc deletion commands. Reason: skills are markdown. Correct ownership proof needs exact content hashing, link and reparse-point checks, marker counting and a recheck right before deletion, and prose instructions cannot make those reliable or testable. Precedents are the installers' own guarded removal functions and the retired `tools/cleanup-memory-graph.sh` tombstone (removed in 2368e95). Helper language and placement are D-S11-3.
  - **The installed helper has no installer mode.** The helper is synced into every agent home's `tools/` (and its proof code is shared with the installers, R-S11-26), so an installed copy must not be able to run the installers' removal path (R-S11-25 to R-S11-27) against any home. The installer-mode entry point is therefore a separate, checkout-only file beside the helper: it reuses the helper's proof code and adds the installer-mode command, and it is excluded from the tools sync by exact path, as the source-only tools are today (Unix `rsync --exclude` list, install.sh:932-948; Windows `-ExcludedExactPaths $sourceOnly`, install.ps1:2551-2561, 2581, 2616). No agent home and no `~/.agents` root ever receives it, and the installed helper accepts no installer-mode argument. File names are fixed in the plan with D-S11-3. As defence in depth, the entry point also refuses to run unless the directory it resolves to lies inside a Git checkout whose root contains `install.sh` and `install.ps1`, and unless it is outside every resolved agent home (`~/.claude`, the configured `CODEX_HOME` or `~/.codex`, `~/.gemini`) and outside `~/.agents` and the roots it links to. "Inside a Git checkout" means a `.git` directory or `.git` file exists at the root that holds `install.sh` and `install.ps1`. When any of these location checks refuses (for example a framework copy extracted from an archive without `.git`), the installer removes no retired skill or agent, keeps them, reports "ownership helper refused: <reason>; kept", and continues the install, as for a missing interpreter in R-S11-26; it never falls back to a name-only or shell-only proof.
- **R-S11-9. Outcome report and idempotence.** After apply, the skill reports removed, kept-ambiguous and kept-unrelated items, using paths only and never file contents. A second dry run reports nothing left to remove except items kept as ambiguous.

### Uninstall scripts

- **R-S11-10. Complete removal for one agent.** `uninstall.sh` (Unix) and `uninstall.ps1` (Windows, PowerShell 5.1 and 7) take a required agent argument, a dry-run option, and the confirmation options of R-S11-23. They never remove anything without one of the two confirmations R-S11-23 allows for them: in an interactive run, the user typing the agent name after the script prints the plan and its digest in that same run; or, in a non-interactive run, `--yes` with `--plan-digest` equal to the digest of the plan recomputed now. Either way, removal is bound to the plan printed in that run. They remove every framework-owned item the installer writes for that agent and layout:
  - `skills/assistant-*` framework skills, current and retired;
  - framework-owned top-level entries under `tools/` and `docs/evals/`;
  - framework agent files;
  - framework Codex rule files;
  - the managed instruction block in `CLAUDE.md`/`AGENTS.md`;
  - retired hook shims and exact retired registrations;
  - on Windows Codex, the `~/.agents/skills/assistant-*` and `~/.agents/tools/{change-impact,progress}` entries;
  - any installer ownership record (D-S11-2).

  The ownership rules of R-S11-3 and the exclusions of R-S11-4 apply, except that current framework items are in scope.
- **R-S11-11. User content stays byte-identical.** Every file and directory not proven framework-owned is unchanged: bytes, existence and, where the platform exposes them, mode and Windows DACL. Compare with the state just before the uninstall run.
  - **Instruction files.** Only the single balanced managed block and the separator line the installer added are removed, and the rest of the file is byte-identical. The installers differ here. Unix keeps the user suffix verbatim after the block and one blank line (install.sh:1155-1165). Windows rewrites the whole file trimmed with platform newlines (install.ps1:2280-2291). "Byte-identical" therefore refers to the pre-uninstall bytes, not to the pre-install original.
  - **Settings files.** Only exact retired registrations are removed. Malformed or non-object settings are preserved with a warning (existing behaviour, install.sh:490, 662).
- **R-S11-12. Refusal on ambiguity.** Ambiguous, duplicate, nested or unbalanced markers leave that instruction file unchanged and reported, as in install.sh:1139-1150, 1182-1183 and install.ps1:2225-2232. A modified framework file, an unknown file inside a framework skill directory, or a linked or reparse-point item is kept and reported. The exit status separates "all owned items removed" from "completed with items kept". There is no override for modified framework files: they are always kept and reported (D-S11-5 (a), decided by user 2026-11-06).
- **R-S11-13. Preflight before any write.** Both scripts compute the full plan and validate every target before the first deletion. Validation covers:
  - type checks and link/reparse checks on each item and its ancestors;
  - a resolved agent home that is not the user home or a filesystem root (install.ps1:2492-2496);
  - no equality or ancestry overlap between the framework checkout and any target (install.ps1:292-302, 2497).

  A preflight failure changes nothing. Running uninstall from an installed copy rather than a checkout is D-S11-6.
- **R-S11-14. Codex execution-policy rules.** Uninstall removes `rules/workflow.rules` only when it matches framework content. It then tells the user that the framework's git-push, force-push, commit, `git reset --hard`, `git branch -D` and `rm -rf` safeguards (codex-rules/workflow.rules:14-60) are no longer installed. It never edits or removes other rule files (for example a user `default.rules`). Cleanup never removes `workflow.rules`. `codex-rules/workflow.rules` in the source is not weakened, and no allow rule is added for cleanup or uninstall commands. The only change to it is the added `prompt` rules of R-S11-24, which strengthen it.
- **R-S11-15. Unix `~/.agents` symlink.** The installer creates `~/.agents` only when it is absent, as a symlink to the Codex home (install.sh:902-919). A user or another tool can create the identical link. Uninstall therefore keeps it and reports it, and never removes it (D-S11-7 (a), decided by user 2026-11-06).

### Retired-item inventory

- **R-S11-16. One source of truth.** The repository holds one retired-item inventory that `install.sh`, `install.ps1`, the cleanup helper and the uninstall scripts all read. No consumer keeps its own copy, with one explicit exception (D-S11-12 (b)): a plain-text list that the helper's data build generates from the inventory for `install.sh`'s Python-less path. It holds only `installer_exact_removal` tool entries whose layout is `unix` (or both), one per line as kind, `node_type` and path separated by tabs, so install.sh applies today's per-entry handling (recursive removal of a directory such as `evals/node_modules`, `rm -f` of files, the link and type guards on `plugins/sync-plugin-skills.sh`, `rmdir` of an empty `plugins`; install.sh:720-788) from the list rather than from a hand-kept mapping. Windows-only entries such as `tools/cleanup-memory-graph.*` never appear in it. It is the only allowed derivative. It is generated, never edited by hand, and a contract test fails when it differs from what the inventory produces. It is limited to the tool entries that carry `installer_exact_removal` at the inventory's introduction (R-S11-19), so it can never name a skill, agent, hook, registration or block. The inventory replaces the hard-coded lists at:
  - install.sh: 389-427 (hook entrypoints, helpers and modules), 720-741 (source-only tools), 743-788 (plugin tool);
  - install.ps1: 49-79 (hook lists), 2551-2566 (source-only and retired tools).

  Each entry records the kind, the installed relative path or name, the agents and layouts it applies to, and, for kinds installed from a tracked source file, the repository source path (`source_path`) and the last main revision whose tree still contains that source path (`retired_in`, R-S11-19). The current Unix/Windows divergence is resolved in the inventory. Windows retires `cleanup-memory-graph.ps1/.sh` by exact path (install.ps1:2562-2566); Unix had no exact-path entry for them until audit F4 added `RETIRED_MANAGED_TOOLS` in install.sh. Neither installer removes the legacy `tools/memory-graph` directory: Unix excluded `/memory-graph` from its whole-root tools sync, which also protected it from `--delete` (install.sh:939 at ad6e598); since audit F4 it is simply not a framework-owned top-level entry, so the sync never touches it, and Windows has no entry for it. The inventory therefore seeds a `managed_tool` directory entry `tools/memory-graph` for all three agents and both layouts, with `source_path` `tools/memory-graph` and `retired_in` fdff2dc (the parent of 7e2fedd, which deleted it), so cleanup and uninstall can prove and remove an untouched copy. It has no `installer_exact_removal`, so the installers still leave it in place (D-S11-8). An installed copy that was ever run holds a `.publish/` build output written by its runner (`run-memory-graph.sh:13-33` at fdff2dc), which fails R-S11-3(c), so such a copy is reported as ambiguous. The Memory Graph provider data is not inside this directory and stays out of scope (Scope).
- **R-S11-17. Content proof data agrees with what the installers wrote.** The content proof (D-S11-2) for each inventory item and each current framework item is derived from repository history. It applies the installers' per-agent `{agent_state_dir}` substitution (install.sh:678-687, 866-879; install.ps1:1853-1865), so an untouched installed copy from any main-branch revision matches. No release tags exist (`git tag` is empty; version.txt is 0.2.0 since the initial commit), so "released" means "reachable from main" unless D-S11-2 decides otherwise. Line-ending handling for Windows checkouts without `.gitattributes` is part of D-S11-2.
- **R-S11-18. Retiring a skill is one data change.** Adding a skill, agent, hook or tool to the inventory, with its content proof, is enough for cleanup and uninstall to handle it, and, for skills and agents, for the installers' automatic removal of proven-owned copies (R-S11-25). S10's three retirements (Telos, Diagrams, Ideate) are the first use.
- **R-S11-19. Inventory schema.** The inventory is persisted data with four consumers (install.sh, install.ps1, the cleanup helper, the uninstall scripts), so it has a schema in the field style of docs/skill-contract-design-guide.md:85-118. "Fail" in `on_missing` means R-S11-21 applies.

  Top level:

  | Field | Type | Required | Validation | on_missing |
  |---|---|---|---|---|
  | `schema_version` | string | true | `MAJOR.MINOR`; the major is one the consumer knows (`1` at introduction) | fail |
  | `entries` | object[] | true | Non-empty; every `id` is unique | fail |

  Each entry:

  | Field | Type | Required | Validation | on_missing |
  |---|---|---|---|---|
  | `id` | string | true | Stable, unique, lowercase, for example `skill/assistant-telos`; never reused for a different item | fail |
  | `kind` | enum | true | One of the `kind` values below | fail |
  | `root` | enum | true | `agent_home`; `agents_skills` (Windows Codex `~/.agents/skills`, install.ps1:2508-2513); `agents_tools` (Windows Codex `~/.agents/tools`, install.ps1:2619-2623) | fail |
  | `path` | string | true | Relative to `root`, forward slashes, no leading slash, no drive letter, no empty, `.` or `..` segment. For `hook_registration` it is the entrypoint path under `hooks/assistant` matched as the first command token. For `instruction_block` it is the instruction file name and the entry also names the marker pair | fail |
  | `node_type` | enum | conditional: every kind except `hook_registration` and `instruction_block` | `file` or `directory` | fail |
  | `agents` | enum[] | true | Non-empty subset of `claude`, `codex`, `gemini` | fail |
  | `layouts` | enum[] | true | Non-empty subset of `unix`, `windows` | fail |
  | `source_path` | string | conditional: `kind` is `skill_directory`, `agent_file`, `hook_entrypoint`, `hook_helper`, `hook_module`, `managed_tool` or `managed_tool_empty_directory`, and `installer_generated` is not true | Repository-relative path the item was installed from, with the same path rules as `path`. Per-kind mapping from the installed `path`: `skill_directory` `skills/<name>` → `skills/<name>` (install.sh:800-805); `agent_file` `agents/<name>.md` → `agents/claude/<name>.md` and `agents/<name>.toml` → `agents/codex/<name>.toml` (install.sh:984-990, 1038-1044; install.ps1:2629, 2633); `hook_entrypoint`, `hook_helper` and `hook_module` `hooks/assistant/<name>` → `hooks/scripts/<name>` (the hook sources were tracked under `hooks/scripts/` until aba2a4f; `git ls-tree -r aba2a4f^ hooks/`); `managed_tool` and `managed_tool_empty_directory` `tools/<rest>` → `tools/<rest>` | fail; for `source_only_tool`, `hook_registration`, `instruction_block` and `installer_generated` entries, not applicable and never read |
  | `retired_in` | string | conditional: `source_path` is required | Full commit id of a commit C, reachable from main, whose tree contains `source_path` and such that no main-reachable descendant of C contains `source_path`. "Descendant" means commit ancestry (`git merge-base --is-ancestor`), not first-parent history: deletions made on side branches and merged later (2368e95, 0e6d4c7, 7e2fedd are not on main's first-parent chain) are covered the same way. If more than one commit qualifies, any one of them is valid. The tree that contains the entry must not contain `source_path`. Two cases. **Retirement made after the inventory exists:** the entry and the deletion of `source_path` land in the same change, never before. C is the commit the removing change is based on. It is known when the entry is written and does not depend on whether the change is merged, squashed or rebased. Validation of such an entry, run against main before the change merges, is: C contains `source_path`; C is an ancestor of the removing commit; and no main-reachable commit that is not an ancestor of C touches `source_path` (`git log main ^C -- <source_path>` is empty). If a main commit touched `source_path` after C and before the merge, the entry's `retired_in` is updated to a qualifying commit in the merge. After the merge, the removing branch's own commits may become main-reachable descendants of C that still contain `source_path`; that does not invalidate the entry, because its validation is the merge-time check above. **Retirement made before the inventory exists** (entries seeded when the inventory is introduced): the same-change rule cannot apply, so `retired_in` must satisfy the general definition. The receipt cannot prove itself through R-S11-3(a) or (b), because it is not an inventory entry and its bytes differ per home. It has its own ownership proof instead, and uninstall removes it only when all of these hold:
  - it is at the single fixed receipt path the plan sets under the agent home (D-S11-2); a file of the same name anywhere else is never treated as a receipt;
  - it is a regular file, and it and every ancestor up to the agent home pass R-S11-3(d);
  - it passes every R-S11-20 validation, including `agent`, `layout` and `agent_home` equal to the current run;
  - its `framework_revision` is a known revision: for uninstall, a commit reachable from main in the checkout running it; for the cleanup helper, which runs from installed tools without a checkout, a revision listed in the shipped content-proof data (R-S11-17).

  If any of the first three checks fails, the receipt is kept and reported as ambiguous, and R-S11-21 applies. **Unknown `framework_revision`.** If only the last check fails (for example, uninstall runs from a checkout older than the installing one, or the helper's data predates the receipt), the receipt is well formed but cannot be trusted as proof. The consumer then keeps the receipt as ambiguous and does not use any receipt-derived ownership; it does not refuse all removals. Proof for every item falls back to the inventory and fingerprint rules (R-S11-3(a)-(f), R-S11-17), exactly as for a home with no receipt under D-S11-2 options (a) and (c); under option (b) this falls under R-S11-21's missing-receipt refusal. The report names the unknown revision and tells the user to update the framework checkout (or reinstall, for the helper's data) and rerun. Uninstall removes the receipt last, after every item it proves. Cleanup never removes the receipt. Compatibility follows the R-S11-19 rule.
- **R-S11-21. Fail closed on inventory and receipt errors.** If the inventory is missing, unreadable, fails any R-S11-19 validation, or has an unknown major `schema_version`, every consumer refuses all removals and reports why. The installers then also skip their own retired-item removal for that run and say so. **Exception, `install.sh` without Python 3.9+ (D-S11-12 (b)):** that path cannot read or validate the JSON inventory, so it is outside this inventory check. It reads only the generated `installer_exact_removal` tool list (R-S11-16) and removes exactly those tool paths with today's exact-path behaviour and guards (R-S11-3(g); install.sh:720-788), and nothing else: no skill or agent removal (R-S11-26), no proof-based removal, no new entries. If that list is missing or unreadable, that path removes no retired tool and says so. The list's agreement with the inventory is enforced by the generation test, not at install time. If a receipt is present but unreadable, fails any R-S11-20 validation, has an unknown major version, or names another agent, layout or home, the cleanup helper and the uninstall scripts refuse all removals for that home and report why. A receipt whose only failure is an unknown `framework_revision` is not in this refusal class: it is handled by R-S11-20's unknown-revision rule (receipt kept as ambiguous, receipt-derived ownership unused, fingerprint and inventory proof still apply). A missing receipt is not an error under D-S11-2 options (a) and (c): proof falls back to fingerprints and the report says "no receipt; fingerprint proof used". Under option (b) a missing receipt, or a receipt with an unknown `framework_revision`, refuses all removals. A consumer never repairs, regenerates or partially trusts a broken inventory or receipt.

- **R-S11-23. Script-level confirmation for uninstall and helper apply.** `uninstall.sh`, `uninstall.ps1` and the cleanup helper's apply mode each enforce confirmation themselves, independent of the calling agent:
  - Every non-dry run first computes and prints the full plan (the R-S11-22 manifest in readable form) and its digest.
  - **Helper apply, every run.** `--manifest <file> --manifest-digest <digest>` are always required, interactive or not. The digest must come from a prior dry run and must equal the recomputed `manifest_digest`, and the manifest's top-level values must equal the current run (R-S11-22). Without both options, or on any mismatch, the helper refuses with no change and a non-zero exit. In an interactive run (standard input and output are a terminal) the helper then also asks the user to type the agent name; any other answer, end of input or interrupt aborts with no change. That prompt is an extra check on top of the manifest binding, never a replacement for it. In a non-interactive run the helper also requires `--yes`.
  - **Uninstall scripts, interactive run** (standard input and output are a terminal, no `--yes`): after printing the plan and its digest in this run, the script asks the user to type the agent name. Any other answer, end of input or interrupt aborts with no change. A typed confirmation removes only items in the plan printed in this run, each re-proved as R-S11-6 states. This typed-confirmation-only path exists for `uninstall.sh` and `uninstall.ps1` only.
  - **Uninstall scripts, non-interactive run:** the script proceeds only with `--yes` together with `--plan-digest <digest>`. The digest must come from a prior dry run and must equal the digest of the plan recomputed now. A mismatch refuses with no change and prints the new digest.
  - A non-interactive run without `--yes`, or `--yes` without the required digest (and, for the helper, without the manifest), refuses with no change and a non-zero exit.

  - **No installer mode in the installed helper.** The confirmation rules above are the only way the installed helper removes anything. The installers' unprompted retired-item removal (R-S11-27) runs only through the checkout-only installer-mode entry point of R-S11-8, which no agent home or `~/.agents` root contains; the installed helper rejects any installer-mode argument with no change and a non-zero exit.

  The cleanup skill always calls the helper non-interactively, in the fixed apply form of R-S11-24. It passes `--manifest`, `--manifest-digest` and `--yes` only after the user has confirmed that exact digest in chat (R-S11-6).
- **R-S11-24. Codex `prompt` rules for destructive entry points.** `codex-rules/workflow.rules` gains `decision="prompt"` rules (never `allow`, never `forbidden`) for the cleanup helper's apply invocation and for `uninstall.sh` and `uninstall.ps1`, in every invocation form the README documents (for example `./uninstall.sh`, `bash uninstall.sh`, and `pwsh -File uninstall.ps1`). The rules strengthen the file, whose precedence is forbidden > prompt > allow (codex-rules/workflow.rules:6), and they come in addition to chat confirmation and R-S11-23, not in place of them. A prefix rule matches only the argv prefix it names (compare the `rm -rf` rule at :57-61), so the plan fixes apply and uninstall invocation forms that a prefix rule can match, for example ones that do not begin with a home-dependent absolute path. The README documents only forms that these prefix rules match. Acceptance and the Codex rules test cover every documented form. Any other form that still works (for example an absolute path to the helper) is recorded in the change as a residual gap, is not documented in the README, and remains covered by R-S11-22 and R-S11-23.
  - **The skill's own helper-apply invocation.** The helper is installed under the configurable agent home (`CODEX_HOME`, R-S11-7), so the natural invocation, an absolute path such as `$CODEX_HOME/tools/<helper-dir>/<helper>.py`, has a first or second argv token that differs per home. Every rule in workflow.rules is a `prefix_rule` whose `pattern` is a list of literal argv tokens compared from the first token, with no path wildcard (codex-rules/workflow.rules:15-79, for example `["rm", "-rf"]` at :57-61), so no rule can list a home-dependent path. SKILL.md therefore invokes helper apply only in one fixed form whose tokens are constant across homes: the working directory set to the resolved agent home, then the interpreter, the helper's path relative to the agent home, and `apply` as the first argument, followed by the option arguments. On Unix that is `python3 tools/<helper-dir>/<helper>.py apply --manifest … --manifest-digest … --yes`; on Windows, `pwsh -NoProfile -File tools/<helper-dir>/<helper>.ps1 apply …` and the same with `powershell` for PowerShell 5.1 (helper names and directory per D-S11-3, fixed in the plan). ### Installer removal of retired skills and agents (D-S11-8, decided (b))

- **R-S11-25. Installers remove proven-owned retired skills and agents automatically.** On every install, including single-skill `--skill`/`-Skill` installs (confirmed by the user 2026-11-06; the installers already run their retired-tool removal for every install: install.sh:922-931; install.ps1:2604-2610), `install.sh` and `install.ps1` remove retired `skill_directory` and `agent_file` items for the agent being installed, in addition to the retired tools and hooks they already remove. The rules:
  - **Same proof as the cleanup helper.** An item is removed only when R-S11-3(a)-(e) all hold: it is an inventory entry for this agent and layout; every file matches framework content by the content proof of D-S11-2 (a fingerprint of a main-reachable revision after `{agent_state_dir}` substitution, R-S11-17, or a valid receipt entry whose `framework_revision` is reachable from main in the installing checkout, R-S11-20); a directory holds no file that fails that proof; and neither the item nor any ancestor up to the agent home is a link or reparse point. The installer-only exact-location rule R-S11-3(g) and the `installer_generated` rule (f) never apply to these kinds. A name match alone never establishes ownership.
  - **Ambiguous items are kept.** An item that fails any part of the proof (modified file, extra user file, link, unknown receipt revision, unreadable content) is kept byte-for-byte and reported with its reason and a pointer to the cleanup skill. The cleanup skill remains the tool for anything ambiguous; the installer never offers an override.
  - **User files byte-for-byte.** Everything not removed under this requirement keeps its bytes, existence, mode and, on Windows, DACL (as R-S11-11 defines for uninstall). The R-S11-4 exclusions apply in full, so a same-named item from another product (`assistant-memory`) is kept as unrelated.
  - **Scope bound.** Only `skill_directory` and `agent_file` entries are added to automatic removal. Retired tools, hooks and registrations keep exactly their current installer behaviour (D-S11-8). `instruction_block` entries and `managed_tool` entries without `installer_exact_removal`, including the seeded `tools/memory-graph`, are never removed by an installer. On Windows Codex the `agents_skills` root (`~/.agents/skills`, install.ps1:2508-2513) is covered with the same rules.
  - **Shared inventory.** The installers read the single retired-item inventory (R-S11-16) and content-proof data (R-S11-17). R-S11-21 applies: when the inventory, the proof data or a present receipt fails validation, the installer removes no retired skill or agent that run and says so.
- **R-S11-26. One shared proof implementation per platform; installers call it.** The installers do not reimplement the ownership proof. Each installer calls the same per-platform proof code as the cleanup skill (D-S11-3), from the framework checkout it is running from, through the checkout-only installer-mode entry point of R-S11-8, never through the installed helper. On Unix, `install.sh` runs that entry point under `$FRAMEWORK_DIR/tools/<helper-dir>/` with `python3`. On Windows, `install.ps1` loads or runs the PowerShell entry point under its checkout's `tools\<helper-dir>\`, which reuses the install.ps1 deletion primitives as D-S11-3 already plans. Reasons from source:
  - The proof needs SHA-256 content hashing, history-derived fingerprint lookup, receipt parsing and link or reparse checks. Neither installer hashes file content today (no `sha256sum`, `shasum`, `Get-FileHash` or SHA-256 use in install.sh or install.ps1 at d11756d), so a second implementation would be new code duplicating the helper.
  - Duplicate implementations of one rule already drift here: install.sh carries the hook-registration rewrite twice, once in jq (install.sh:488-568) and once in Python (:570-660), and the two installers' retired lists already differ (R-S11-16). One implementation per platform is the only way to keep installer and cleanup proofs identical.
  - The Unix helper's interpreter is already required for the default install: install.sh requires Python 3.9+ whenever the selected closure includes `assistant-workflow` (install.sh:88-98), which the default all-skills install does. If `python3` 3.9 or later is not available (for example a single-skill install of a skill without Workflow on a machine without Python), install.sh removes no retired skill or agent, keeps them, reports "ownership helper unavailable; kept", and continues the install. It never falls back to a name-only or shell-only proof.
- **R-S11-27. Installer-time removal is bounded and reported, with no new prompt.** Installer removal keeps the helper's safety properties, adjusted for a run with no chat confirmation:
  - **Plan before any write.** The installer mode computes the full removal plan before its first deletion, as part of the installer's existing preflight, so a preflight failure anywhere in the install removes nothing. The plan has the R-S11-22 manifest shape with `operation` `install`. Before deleting, the installer prints each item it will remove (path and kind), each item it keeps (path and reason), and the manifest digest. Paths only, never file contents.
  - **Dry run.** `install.sh --dry-run` and `install.ps1 -DryRun` print the same plan and digest and change nothing, with the dry-run guarantees of R-S11-5 (no file or directory created in the agent home, no content, mode, ownership or modification-time change).
  - **Bound to the printed plan.** Apply in installer mode removes only items in the plan computed in that run, re-proves each one immediately before deleting it (R-S11-6, third bullet) and skips and reports any item whose type, link status, content or digest changed. It never scans for further candidates after the plan is printed.
  - **No interactive confirmation or opt-in flag.** Removal runs without a prompt or new flag. This matches current installer behaviour: neither installer prompts at all (no `read -p` in install.sh, no `Read-Host` in install.ps1), both remove retired tools without asking (install.sh:720-788; install.ps1:2604-2610), and install.sh already documents that reinstalling overwrites manual changes inside installed skill directories (install.sh:45-46). The confirmation gap is bounded by proof strength instead: the installer removes only items whose every byte matches a framework revision, which a reinstall from that revision would have written anyway, and keeps every ambiguous item for the confirmed cleanup flow. The user's 2026-11-06 decision selected this automatic behaviour.
  - **Not a bypass of helper apply.** The installer mode accepts no `--manifest` and cannot remove current items, registrations or instruction blocks. It exists only in the checkout-only entry point of R-S11-8, which the tools sync never copies into any agent home or `~/.agents` root, so an installed helper copy cannot run it against its own home or another agent's (for example a copy under `~/.codex` invoked with `--agent claude`), and R-S11-24's prompt rules need not match it. As defence in depth, that entry point also refuses to run outside a Git checkout containing `install.sh` and `install.ps1`, or from inside any resolved agent home or `~/.agents` root (R-S11-8). ## Unresolved decisions

- **D-S11-1 (technical default). Skill name.** `assistant-cleanup` versus `assistant-uninstall-legacy` or similar. It must start with `assistant-`, because installers discover only `assistant-*` (install.sh:805; install.ps1:2472). **Default: `assistant-cleanup`**, provided the description wording passes the activation-precision contracts against the "clean up code" near-misses. If it does not, choose a more specific name.
- **D-S11-2 (technical_design_decision). Content proof.**
  - (a) Fingerprints of every main-reachable revision of each framework file, per agent substitution, generated by a repository tool and shipped as data. This works for homes installed before S11.
  - (b) An installer-written receipt in each home, listing installed paths and hashes. This is exact for future installs, but gives no proof for existing homes and is itself a file to protect and remove.
  - (c) Both: receipt first, fingerprints as the fallback.

  The receipt shape is R-S11-20 and the fail-closed rule is R-S11-21.

  **Default: (c).** Existing homes need (a). (b) avoids history scans for items installed after S11 and records Windows-normalized instruction state. The data has real consumers (cleanup, uninstall, installer), so it is not the "metadata registry" that docs/skill-contract-design-guide.md:24-28 forbids. Line endings: hash after normalizing CRLF to LF for text extensions the installer substitutes, and hash all other files raw. Confirm this against a native Windows checkout before adopting it.
- **D-S11-3 (technical default). Helper language and placement.** Unix options are Bash with `shasum`/`sha256sum`, or Python 3. Windows options are a PowerShell helper reusing the install.ps1 primitives, or Python. **Default:** Python 3 on Unix, for portable hashing, JSON and path handling. The Unix installer already depends on `python3` as a JSON fallback (install.sh:570), and Workflow requires it (install.sh:88-98). Use PowerShell on Windows, so Windows does not gain a Python dependency outside Workflow. Place the helpers under a new `tools/` subdirectory so the existing tool sync installs them. How install.ps1 primitives are shared without the installer consolidation is decided in the plan.

Cleanup skill and uninstall requests.** (a) The skill recognises "uninstall the framework" and only gives the user the exact uninstall command for their platform and agent. (b) The request is a negative case, and the skill does not activate. **Default: (a).** It avoids a dead end, and the skill runs nothing destructive for uninstall. **Decided by user 2026-11-06: (a), the skill gives the uninstall command.** R-S11-1 and its acceptance examples state that behaviour.

### Plan-time notes

These are notes for the implementation plan, not requirements. Each serves a requirement above.

- **No bytecode cache in the dry run.** The Unix helper lives under the agent home (`tools/<helper-dir>/`, D-S11-3), so a `__pycache__/` written beside an imported module would be a new directory inside the agent home and break R-S11-5. Python writes bytecode only for imported modules, not for the script it runs, so either keep the helper a single file that imports only the standard library, or set `sys.dont_write_bytecode = True` before importing any local module. Do not use `python3 -B`: it adds an argv token and changes the fixed apply form that the Codex `prompt` rules match (R-S11-24). The installers' `__pycache__` exclusion (install.sh:937; install.ps1:2549) only affects the copy and does not prevent this.
- **Interactive detection.** Define an interactive helper run as "standard input and output are a terminal and `--yes` is absent", the same definition R-S11-23 uses for the uninstall scripts. Otherwise the skill's non-interactive `--yes` call made from a host that supplies a terminal would still stop at a typed prompt.
- **No options before `apply`.** The helper refuses any argument placed before `apply` (for example `helper.py --yes apply …`). Codex prefix rules compare argv from the first token with no wildcard (codex-rules/workflow.rules:15-17, 57-61), so a leading option would move `apply` out of the prefix the `prompt` rule names and escape it (R-S11-24).
- **Source path for `source_only_tool` fingerprints.** These entries carry no `source_path` (R-S11-19), so the content-proof generator infers `tools/<rest>` from the installed `tools/<rest>`. The Unix installer copies `$FRAMEWORK_DIR/tools/` to `$AGENT_HOME/tools/` (install.sh:819-820, 932-949), and the Windows installer does the same per top-level entry (install.ps1:1367-1419).
- **Directory digests and links.** A directory digest (R-S11-22 `items[].digest`) records a symbolic link as an entry of type link with its target string, and never follows it or hashes what it points to. This matters most for an `installer_generated` item such as `tools/evals/node_modules`, which may hold links that R-S11-3(f) never follows; a changed link target then changes the digest, so R-S11-6 skips the item.
