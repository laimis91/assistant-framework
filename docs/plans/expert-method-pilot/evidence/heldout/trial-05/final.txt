The bundle demonstrates a **race between checking the completion cache and recording the payment result**. Two overlapping requests with the same checkout key can both create accepted payments.

In [`Checkout.post()`](/private/tmp/expert-pilot-runtime-20261022/trial-05/subject/replay.py:26):

1. Each request checks `completed` while holding `cache_lock`, then releases the lock.
2. Both can observe a missing receipt before either records completion.
3. Both call `gateway.charge(key)` without rechecking or reserving the key.
4. Both write their receipts to the same cache entry; the last write wins.

The [gateway lock](/private/tmp/expert-pilot-runtime-20261022/trial-05/subject/replay.py:13) serializes payment creation, but every call creates another accepted payment. It performs no deduplication by checkout key.

I ran all four combinations:

| Schedule | Keys | Observed result |
|---|---|---|
| Parallel | Same | Two accepted payments for `order-17`; both replies `cached: false` |
| Serial | Same | One accepted payment; second reply `cached: true` |
| Parallel | Distinct | Two accepted payments, one per key |
| Serial | Distinct | Two accepted payments, one per key |

Reproduce from the working directory with:

```sh
python3 -B subject/replay.py --schedule parallel --keys same
```

The observed duplicate payments had different receipts, `receipt-1` and `receipt-2`, while `completed` contained only `receipt-2`. Inspecting only the completion cache would therefore conceal the extra accepted payment.

The parallel replay uses a barrier immediately after cache lookup to force both requests to observe the miss. This controls scheduling without altering payment or cache contents. The necessary conditions are overlapping same-key requests that both miss the cache, followed by gateway acceptance of both charge calls. Changed retry keys, network errors, timeouts, and multiple processes are unnecessary for this reproduction. Distinct-key runs do not establish a duplicate for one checkout.

The bundle establishes the mechanism, but not its frequency or whether the reported production incident followed this sequence. A narrow next step is to correlate one affected checkout’s request keys, lookup/completion timestamps, and gateway receipts to establish whether both requests missed before either recorded completion.
