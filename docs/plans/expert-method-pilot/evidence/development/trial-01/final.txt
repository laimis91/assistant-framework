The default failure is **contention on the admission lock**, caused by the background refresh. The request times out before starting a database query.

The refresh holds the lock for 120 ms ([source](/private/tmp/expert-pilot-runtime-20261022/trial-01/subject/service.py:18)). The request allows only 50 ms to acquire it, then raises the compatibility exception `DatabaseTimeout` when acquisition fails ([source](/private/tmp/expert-pilot-runtime-20261022/trial-01/subject/service.py:27)).

Local observations isolate the cause:

| Configuration | Observed result | Queries started |
|---|---|---:|
| Defaults | Admission failed after 52.2 ms | 0 |
| Database delay reduced to 0 ms | Admission still failed | 0 |
| Refresh hold reduced to 0 ms | Succeeded; database stage 5 ms | 1 |
| Timeout increased to 200 ms | Succeeded after 125 ms admission wait | 1 |
| No refresh hold, database delay 80 ms | Failed at database stage | 1 |

The last comparison confirms that the same exception also represents a database-stage timeout. Its name alone cannot identify the failing stage; the default trace does.

The bundle establishes this cause for its synthetic workload. It does not explain why refresh needs to hold admission throughout its work or establish production behavior. The narrow next step is to review that lock’s intended scope; production confirmation would require admission-wait and query-start observations.
