# Architecture Documentation Generator

## Protocol

For any existing-system feature-preparation scope, infer `feature_preparation_evidence_status` before mapping or drafting; incomplete evidence returns `feature_preparation_evidence_trace outcome=blocked_incomplete_evidence` with `request_complete_evidence` and no documentation write even when no Architecture Decision Pack applies. Every carried behavior claim or Product question must retain an exact `{evidence_ref, item_id, claim_or_question}` binding to its admissible canonical evidence row; broad artifact-only, stale, or mismatched bindings are incomplete evidence. When the scope carries a workflow Architecture Decision Pack, also infer `architecture_decision_pack_status`. For `current`, preserve only the compact canonical `architecture_decision_pack` projection: ref, mode, freshness basis, facts, assumptions, material questions, boundaries/dependencies, design-pressure checks, review-intensive challenge evidence, Type Ledger, quality scenarios, verification/rollback, and invalidators. Resolve the selected design and rationale through the current canonical Pack ref, then record the resulting decision refs in `documented_decision_refs`. Every carried Product question needs admissible feature-preparation evidence covering requirements/design, current implementation, behavioral tests, conflict analysis, and evidence gaps. A fresh Pack with incomplete evidence returns `architecture_decision_pack_trace outcome=blocked_incomplete_pack` and `recovery_action=request_complete_pack`; do not document or propagate that question. Return `documented` only when the exact required bindings resolve. If the ref cannot resolve decisions or currentness cannot be proven, use `missing` or `stale` status and recovery. For `missing`, `stale`, `out_of_scope`, or incomplete preparation evidence, stop that decision's documentation. Never reconstruct, infer, or invent a missing or stale Architecture Decision Pack. Treat semantically incomplete feature-preparation evidence the same way: request completion rather than documenting it. Safe recovery may produce no documentation file. If no Pack applies, do not manufacture one just to write a system overview.

### Step 1: Map the System

Use Code Mapper or manual exploration to identify:

- **Entry points**: Program.cs, Startup, Main, endpoints
- **Layers**: presentation, application, domain, infrastructure
- **Key abstractions**: interfaces, base classes, shared contracts
- **Data flow**: request → handler → service → repository → database
- **External dependencies**: databases, APIs, message queues, file systems
- **Configuration**: appsettings, environment variables, feature flags

### Step 2: Identify Architecture Pattern

Determine what pattern the project uses:
- Clean Architecture / Onion
- N-tier / Layered
- Vertical Slices
- CQRS
- Microservices
- Monolith
- Hybrid

State the pattern and note any deviations.

### Step 4: Include Diagrams

Generate Mermaid diagrams for:
1. **Component diagram** — boxes and arrows showing major components
2. **Data flow** — sequence diagram for primary operation
3. **Dependency graph** — which projects/assemblies reference which

If `assistant-diagrams` skill is available, delegate diagram generation to it.

### Step 5: Verify

- Every component mentioned exists in the codebase
- Every dependency listed is real (check .csproj references, using statements)
- Data flow matches actual code path (trace it)
- No hallucinated components or relationships
- For any Architecture Decision Pack, its source/revision freshness, facts versus assumptions, ownership/type boundary, design-pressure checks, compatibility/extension seam, and verification/rollback link are preserved
- No memory, performance, or extensibility benefit is presented as fact without workload, budget/explicit unknown, measurement method, and failure condition

### Output Location

- `docs/architecture.md` (or update existing)
